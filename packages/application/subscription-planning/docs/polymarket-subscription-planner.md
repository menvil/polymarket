# PolymarketSubscriptionPlanner — какие рынки ещё можно приобрести

## Проблема

`MarketUniverse` отвечает, какие рынки технически существуют. `Policy`
отвечает, какие из них нужны потребителю. Ни один из них не отвечает на
третий вопрос, без которого подписка невозможна:

> какие из желаемых рынков ещё можно ЗАКОННО приобрести для будущей
> физической подписки?

Вопрос отдельный, потому что на него влияет не вкус потребителя, а
жизненный цикл рынка: к идущему рынку присоединяться поздно, до старта
нужен запас на подготовку, а policy к моменту старта может быть уже другой.

## Решение

Чистая синхронная функция без состояния, без часов и без побочных эффектов:

```ts
export class PolymarketSubscriptionPlanner {
  public constructor(config?: PolymarketSubscriptionPlannerConfig);

  public plan(
    entries: readonly MarketDiscoveryEntry[],
    policy: PolymarketPolicy,
    now: Timestamp,
  ): PolymarketSubscriptionPlan;
}
```

Планировщик принимает ЗАПИСИ, а не `MarketUniverse`: живой рантайм передаёт
`universe.getAll()`, тест — литеральный массив, backtest — записи из архива,
и все трое получают одну и ту же логику.

## Две плоскости

```text
CONTROL PLANE

Polymarket V2 Discovery
        ↓
MarketDiscoverySnapshot
        ↓
MarketUniverse ── getAll() ──┐
                             ├──► PolymarketSubscriptionPlanner
PolymarketPolicy ────────────┤              ↓
now ─────────────────────────┘   упорядоченные пригодные рынки

─────────────────────────────────────────────────────────────

DATA PLANE

пока НЕ часть этого контура
```

**Planner does NOT subscribe.** Ни подготовки рынка, ни постановки на поток
данных, ни владельцев, ни claim-ов, ни счётчиков ссылок здесь нет: всё это
появится слоем ниже — там, где впервые возникает физический ресурс.

## Ворота пригодности (порядок фиксирован)

```text
1. чужая площадка          → wrongVenue
2. терминальное состояние  → inactive
3. торги уже идут          → alreadyStarted
4. запаса до старта нет    → insufficientLeadTime
5. policy не подходит      → policyMismatch
6.                         → eligible
                              ↓
                        MarketScorer.rank()
```

Порядок не декоративный. Каждая запись обязана попасть **ровно в одну**
категорию — иначе диагностика перестаёт отвечать на вопрос «по какой ПЕРВОЙ
причине запись не дошла до плана».

Policy проверяется последней намеренно: уже начавшийся рынок нельзя
приобрести независимо от policy, и прогонять по нему ключевые слова и пороги
ликвидности — работа впустую ради ответа, который заведомо не изменится.

## Почему это сделано так: три решения

### 1. Policy оценивается в `market.startsAt`, а не в `now`

```text
сейчас 17:59:30

BTC-policy: … 18:00)      XRP-policy: [18:00 …

рынок XRP 18:00–18:05
```

Подписаться на рынок 18:00 надо ЗАРАНЕЕ — в 17:59:30, когда XRP-policy ещё
не действует. Спроси мы `matches(entry, policy, now)`, XRP-policy не увидела
бы ни одного своего рынка до 18:00, а в 18:00 подписываться уже поздно.
Поэтому вопрос звучит «будет ли policy действовать В МОМЕНТ СТАРТА этого
рынка», и policy может строить план **до собственного `effectiveFrom`**.

Обратная сторона того же правила: BTC-policy с `effectiveUntil = 18:00` НЕ
получит рынок, стартующий ровно в 18:00, хотя прямо сейчас она действует.
Окно policy полуоткрыто, стык принадлежит следующей policy.

### 2. Рынок никогда не приобретается после старта

Требуется строгое `now < market.startsAt`:

| `now` относительно старта | результат        |
|---------------------------|------------------|
| `startsAt - 1 мс`         | пригоден         |
| `startsAt`                | `alreadyStarted` |
| `startsAt + 1 мс`         | `alreadyStarted` |

Догонять начавшийся рынок новый рантайм не умеет и не должен: часть его
данных уже прошла мимо, и подписка дала бы неполную картину, по виду
неотличимую от полной.

После этой проверки идёт запас времени: `startsAt - now >= minLeadTimeMs`.
Отклонение — при **строгом** `<`, поэтому запас ровно в минимум ещё
проходит:

| `startsAt - now`, мс | при `minLeadTimeMs = 120 000` |
|----------------------|-------------------------------|
| 120 001              | пригоден                      |
| 120 000              | пригоден                      |
| 119 999              | `insufficientLeadTime`        |

Отклонение по запасу **не запоминается**: планировщик stateless, а время до
старта убывает монотонно, поэтому повторный отказ получается сам собой.
Кэш «отклонён по lead time» прежнего координатора не переносится.

### 3. Точное начало торгов — единственный источник расписания

Прежний координатор, не имея точного начала, оценивал его как «истечение
минус номинальная длительность». После перехода на canonical `Market` такой
оценки больше нет: рынок вообще не становится canonical, пока точное начало
торгов неизвестно. Арифметики над сроком истечения в пакете нет ни в одной
строке, и это проверяется структурным тестом.

## Конфигурация

```ts
export interface PolymarketSubscriptionPlannerConfig {
  readonly minLeadTimeMs?: number; // по умолчанию 120 000 (2 минуты)
}
```

Значение по умолчанию — parity с прежним координатором сбора; сам
координатор при этом не импортируется. Проверка при создании: конечное,
целое, `>= 0`. Некорректное значение — `ValidationError` сразу, а не тихо
неработающая проверка запаса (`NaN` в сравнении даёт `false` молча).

Чего в конфигурации СОЗНАТЕЛЬНО нет:

- **горизонта планирования** — universe уже ограничен окном discovery;
- **лимита количества** (`maxMarkets`, `topN`) — «сколько держать» зависит
  от владельца: стратегии нужен один ближайший рынок, коллектору — десять.
  Планировщик отдаёт ВСЕ пригодные в правильном порядке, а срез делает
  потребитель: `plan.candidates[0]`, `plan.candidates.slice(0, 3)`.

## Результат

```ts
export interface PolymarketSubscriptionPlan {
  readonly plannedAt: Timestamp;
  readonly candidates: readonly MarketDiscoveryEntry[];
  readonly diagnostics: PolymarketSubscriptionPlanDiagnostics;
}
```

Заморожены план, массив кандидатов и диагностика. Кандидаты — ТЕ ЖЕ объекты
записей, что пришли на вход: обёртка вида `PlannedMarket { entry, score }`
не добавила бы ни одного факта, зато материализованный «score» пережил бы
своё вычисление и поехал бы дальше по контуру как свойство рынка, которым
никогда не был.

`plannedAt` — ровно переданный `now`: планировщик часов не читает, поэтому
план нельзя истолковать в момент, отличный от того, в котором он посчитан.

### Диагностика

```ts
export interface PolymarketSubscriptionPlanDiagnostics {
  readonly scanned: number;
  readonly wrongVenue: number;
  readonly inactive: number;
  readonly alreadyStarted: number;
  readonly insufficientLeadTime: number;
  readonly policyMismatch: number;
  readonly eligible: number;
}
```

Инвариант, проверяемый тестом:

```text
scanned = wrongVenue
        + inactive
        + alreadyStarted
        + insufficientLeadTime
        + policyMismatch
        + eligible
```

Пустой план без диагностики не отличает «policy никому не подошла» от «мы
опоздали ко всем рынкам» и от «universe весь с чужой площадки» — три разные
ситуации с тремя разными действиями.

## Что переиспользуется, а не переписывается

| Вопрос                       | Кто отвечает                    |
|------------------------------|---------------------------------|
| подходит ли рынок policy     | `MarketFilter` (`@polymarket/policy`) |
| в каком порядке брать рынки  | `MarketScorer` (`@polymarket/policy`) |
| можно ли ещё приобрести      | `PolymarketSubscriptionPlanner` |

Второго матчера policy и второго компаратора в пакете нет. `MarketFilter` и
`MarketScorer` создаются внутри планировщика, а не инжектируются: оба — чистые
функции без состояния, и возможность подменить их снаружи означала бы
возможность применить ВТОРОЙ набор правил отбора.

Поскольку начавшиеся рынки исключены ДО ранжирования, `candidates[0]` —
ближайший **доступный** будущий рынок, а не самый старый из всех (сам по
себе `MarketScorer` сортирует по абсолютной хронологии и ничего не
отбрасывает).

## Пример

```ts
const planner = new PolymarketSubscriptionPlanner();

const plan = planner.plan(universe.getAll(), xrp5mPolicy, now);

const next = plan.candidates[0];            // ближайший доступный рынок
const batch = plan.candidates.slice(0, 10); // сколько брать — решает потребитель

plan.diagnostics.insufficientLeadTime;      // почему остальных нет в плане
```

Сценарий смены policy в 17:57 при universe `BTC 17:55`, `BTC 18:00`,
`XRP 18:00`, `XRP 18:05`:

- BTC-policy (`effectiveUntil = 18:00`) не получает ничего: `BTC 17:55` уже
  идёт, `BTC 18:00` — за границей её окна В МОМЕНТ СТАРТА;
- XRP-policy (`effectiveFrom = 18:00`) получает `XRP 18:00`, `XRP 18:05` —
  в этом порядке, за три минуты до собственного `effectiveFrom`.

## Что остаётся следующему слою

`Polymarket Shared Subscription Controller`:

```text
owner (стратегия / коллектор) + Policy
            ↓
        Planner
            ↓
   owner выбирает нужные N
            ↓
   Subscription Claims
            ↓
первый claim  → подготовка рынка → физическая подписка
следующий     → переиспользование
последний снят → физическая отписка
```

Там появятся владельцы, claim-ы и причины, счётчики ссылок, резервирование
на время открытия, обращение к драйверу площадки и транзакционный откат.
Планировщик о них не знает и знать не должен.
