# MarketFilter — отбор записей universe по owner policy

## Проблема

`MarketUniverse` содержит всё, что контур технически способен вести. Нужно
ответить на другой вопрос: какие из этих рынков нужны **конкретному**
потребителю — с его активами, номиналами серий, порогами и словарём.

## API

```ts
export class MarketFilter {
  public matches(entry, policy, evaluationTime): boolean;
  public filter(entries, policy, evaluationTime): MarketDiscoveryEntry[];
}
```

`matches()` — основной атомарный API, `filter()` — оболочка над ним.
Поэлементное совпадение этих двух путей закреплено тестом: именно оно
позволяет планировщику пользоваться атомарным API, не рискуя получить
другой отбор.

### Зачем отдельный `matches()`

Момент оценки выбирает **вызывающий**, а не фильтр. Следующий MR будет
спрашивать «подойдёт ли рынок к моменту СВОЕГО старта»:

```ts
const matchingFuture = universe
  .getAll()
  .filter((entry) => filter.matches(entry, policy, entry.market.startsAt));
```

Поэтому `market.startsAt` не зашит внутрь фильтра: зашитый, он отвечал бы
только на вопрос «подходит ли сейчас» и молча ломал бы планирование.

## Порядок проверок

От дешёвых к дорогим: текстовые селекторы стоят последними, потому что
прогон регекса дороже сравнения полей.

Момент КОМПИЛЯЦИИ регексов у двух методов разный, и это не деталь:

- `matches()` компилирует их только если запись дошла до шага 8 — на одной
  записи компиляция ради заведомо отсеянного рынка была бы чистой тратой;
- `filter()` компилирует их ОДИН раз до обхода и переиспользует на всех
  записях (см. [ниже](#однократная-компиляция)).

Сами проверки:

| № | Проверка | Пусто/отсутствует |
| --- | --- | --- |
| 1 | окно policy (`isPolicyEffectiveAt`) | окна нет — действует всегда |
| 2 | семейство `policy.family === market.family` | обязательно |
| 3 | обязательная спецификация семейства | — |
| 4 | актив в `policy.assets` | ограничения нет |
| 5 | **номинал** в `policy.durations` | ограничения нет |
| 6 | `metrics.liquidity >= policy.minLiquidity` | ограничения нет |
| 7 | `metrics.spread >= policy.minSpread` | ограничения нет |
| 8 | текстовые селекторы | ограничения нет |

## Номинал серии, а не фактическое окно

Шаг 5 сравнивает `market.crypto.duration` — **номинал серии** — и никогда
`market.duration()`.

Это не придирка: площадка вправе сдвинуть окно конкретного рынка, и тогда
5-минутный рынок фактически длится 4 минуты. Сравнение с фактическим окном
выбросило бы его из собственной серии, хотя `durations: [5m]` означает
именно «рынки 5-минутной серии», а не «окна длиной ровно 5 минут».

Инвариант закреплён регрессионным тестом: номинал `5m`, фактическое окно
`4m`, policy `[5m]` → **MATCH**.

## Обязательная спецификация семейства (шаг 3)

Правило безусловное: у `CRYPTO_UP_DOWN` спецификация `crypto` обязательна,
и запись без неё не подходит **никакой** policy этого семейства. У
`BINARY_OUTCOME` спецификация, наоборот, запрещена инвариантом домена —
и там она не требуется.

Проверка вынесена из селектора активов намеренно. Пока она жила внутри
него, одна и та же испорченная запись получала **разные ответы** в
зависимости от того, ограничил ли потребитель активы, — хотя испорченность
записи от policy никак не зависит.

Это защита в глубину: `Market.create()` уже делает такую запись
непредставимой (`_validateFamily` требует `crypto` у `CRYPTO_UP_DOWN`).
Проверка существует ради единообразия правила и на случай записи,
собранной в обход canonical-фабрики.

## Ликвидность и валюта

Сравнение только через `MoneyService.isGreaterThanOrEqual`, который сам
проверяет совместимость валют. При несовместимых валютах — `false`.

Из трёх вариантов это единственный безопасный:

| Вариант | Последствие |
| --- | --- |
| бросить | одна запись роняет отбор всего universe |
| пропустить | рынок отдаётся с НЕпроверенным порогом под видом проверенного |
| **отклонить** | односторонняя ошибка: рынок не взят, порог не нарушен |

## Спред: отсутствие наблюдения не отклоняет рынок

`metrics.spread === undefined` означает «площадка не сообщила спред», а не
«спред нулевой». Рынок в этом случае **не отклоняется** — поведение
мигрировано из старого фильтра намеренно и помечено в коде и тестах.

Отдельного селектора `requireSpread` («не брать рынок без известного
спреда») нет: его добавление — осознанное решение потребителя, а не побочный
эффект миграции.

## Текстовые селекторы

| Селектор | Правило |
| --- | --- |
| `required` | все слова должны присутствовать |
| `anyOf` | хотя бы одно |
| `excluded` | ни одного |

Матчинг регистронезависимый, спецсимволы regex экранируются (`$50`, `c++`,
`a.b`, `foo(bar)` безопасны), слово не матчится как часть большего:

```text
war  матчит:     war, WAR, the-war, war?
war  НЕ матчит:  reward, forward, warrior
```

### Границы слова — Unicode, а не ASCII

```text
(?<![\p{L}\p{N}\p{M}]) … (?![\p{L}\p{N}\p{M}])   флаги iu
```

ASCII-класс `[a-zA-Z0-9]` считал бы любую нелатинскую букву пунктуацией, и
`Биткоинup` совпал бы с `up`. Класс `\p{M}` нужен отдельно: в разложенной
форме (NFD) последним символом слова оказывается комбинирующий знак, а не
буква. Тот же приём и то же обоснование, что в `PolymarketCryptoUpDownClassifier`.

Флаг `g` **не** ставится сознательно: с ним `RegExp.test` тащит `lastIndex`
между вызовами, и один регекс, переиспользованный по списку рынков, давал бы
разные ответы на одинаковых текстах.

### Одно правило на пакет

Само правило совпадения (`compileKeywordRegex`) живёт в отдельном модуле
`keywordMatching.ts`, потому что нужно ДВУМ местам с разными вопросами:

| Кто | Вопрос |
| --- | --- |
| `MarketFilter` | совпадает ли слово с вопросом рынка |
| `createPolymarketPolicy` | эквивалентны ли два слова (поиск противоречий) |

Пока реализации были независимы, они разошлись — и разошлись незаметно:
фабрика сравнивала слова через `toLowerCase()`, матчер — регексом под `iu`.

```text
'S'.toLowerCase() === 'ſ'.toLowerCase()   → false   (фабрика: конфликта нет)
/S/iu.test('ſ')                           → true    (матчер: одно слово)
```

Policy `required: ['S'], excluded: ['ſ']` проходила валидацию, будучи
невыполнимой. Теперь эквивалентность выводится из самого матчера
(`areKeywordsEquivalent`), поэтому разойтись с собой он не может.

Эквивалентность — **взаимная**: регекс `a` совпадает с `b` И наоборот.
Односторонней проверки недостаточно, `regex('war').test('war war')` даёт
`true`, хотя это вхождение, а не равенство.

### Однократная компиляция

`filter()` компилирует регексы один раз на вызов и переиспользует их на всех
записях; `matches()` компилирует их сам, но только если запись дошла до
шага 8. На обходе universe в несколько сотен рынков разница между «один раз»
и «на каждой записи» — это вся стоимость фильтрации.

Общее место для «скомпилировать» и «проверить» — внутренний `KeywordMatcher`.
Он не экспортируется: снаружи контур знает только `MarketFilter`, а второй
публичный тип означал бы, что policy можно применять в обход фильтра.

## Что НЕ перенесено из старого фильтра

| Механизм | Почему |
| --- | --- |
| дедупликация по `marketId` | identity `venueId + marketId` уже гарантируют Discovery и `MarketUniverse`; фильтр не должен второй раз чинить source of truth |
| `maxMarketsToReturn` | количество выбирает потребитель — `ranked.slice(0, n)` |
| `minTimeToExpiryHours` | lifecycle/lead-time, принадлежит Subscription Planner |
| duration через `eventStartMs`/`expiresAt` | относилась к старому `DiscoveredMarket`; источник истины теперь номинал серии |

Фильтр не ранжирует и не мутирует вход; порядок входа сохраняется —
переупорядочивание здесь молча подменяло бы работу `MarketScorer`.
