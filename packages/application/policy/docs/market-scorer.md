# MarketScorer — детерминированный порядок записей universe

## Проблема

После отбора остаётся множество подходящих рынков. Потребителю нужен не
набор, а последовательность: «какой брать первым». Ответ обязан быть
воспроизводимым — два прогона над одним universe не имеют права разойтись,
иначе поведение системы начинает зависеть от порядка, в котором площадка
вернула страницы каталога.

## Решение

Чистая ранжирующая функция без состояния и без часов:

```ts
export class MarketScorer {
  public rank(entries: readonly MarketDiscoveryEntry[]): MarketDiscoveryEntry[];
}
```

Вход не мутируется, записи возвращаются теми же объектами.

## Составной ключ

```text
1. market.startsAt    ASC   ← начало торгов, абсолютная хронология
2. market.expiresAt   ASC   ← второй ключ расписания
3. metrics.liquidity  DESC  ← полезный tie-breaker
4. market.venueId     ASC   ┐ identity: строгий полный порядок
5. market.id          ASC   ┘
```

Ликвидность стоит **ниже обоих ключей расписания**, поэтому по построению
не может перебить более ранний старт. Хвост из identity делает сравнение
строгим полным порядком: равных элементов не остаётся, и результат не
зависит от порядка входа.

`Timestamp` сравнивается canonical-операциями `isBefore`/`isAfter`, а не
разностью `toNumber()`.

## Почему первичный ключ — `startsAt`, а не `expiresAt`

Старый скорер ранжировал по `expiresAt`, и для своего контура это было
верно: он выбирал среди **уже активных** кандидатов, где «ближайшее
истечение» и означает «самый срочный».

Новый universe содержит будущие рынки. Ранжирование по истечению склеило
бы два разных вопроса: 5-минутный рынок, начинающийся через час, истекает
раньше 4-часового, начинающегося сейчас, — и оказался бы первым, хотя
торговать в нём ещё нечего.

## ⚠️ Порядок АБСОЛЮТНЫЙ: уже начавшиеся рынки идут первыми

`ranked[0]` — самый ранний по началу торгов **из поданных**, а не
«ближайший предстоящий». Это разные вещи, и разница не теоретическая.

Discovery набирает снимок фильтром **только по `endDate`**:

```text
endDate ∈ [now − zombieGraceMs, now + endDateWindowMs]
```

По началу торгов ограничения нет вообще, поэтому уже идущий рынок (старт в
прошлом, истечение впереди) попадает в universe штатно. Его `startsAt`
меньше любого предстоящего — значит он и встанет первым, а при нескольких
идущих первым будет **самый старый** из них.

Получить именно ближайший предстоящий — задача вызывающего: он ограничивает
набор по моменту оценки ДО ранжирования.

```ts
const now = clock.nowTimestamp();
const wanted = filter.filter(universe.getAll(), policy, now);
// Без этого шага вершиной стал бы самый СТАРЫЙ из уже идущих рынков.
const upcoming = wanted.filter((entry) => !entry.market.isStartedAt(now));
const next = scorer.rank(upcoming)[0];
```

Почему это не спрятано внутрь скорера: «только предстоящие», минимальный
lead time и «никогда не присоединяться к уже начавшемуся рынку» — это
lifecycle подписки. Он принадлежит следующему Subscription Control MR, и
внесение его сюда дало бы скореру право **отбрасывать** записи.

Поведение закреплено тестом, а не оставлено на удачу.

## Скорер ничего не отбрасывает

Ни policy, ни актив, ни длительность, ни ключевые слова, ни окно
применимости. Разделение строгое:

| Компонент | Вопрос |
| --- | --- |
| `MarketFilter` | подходит / не подходит |
| `MarketScorer` | в каком порядке |

Скорер, умеющий отбрасывать, превращает отбор в функцию порядка входа:
результат начинает зависеть от того, в каком месте списка стоял рынок, а не
от его свойств.

## Почему поля `score` больше нет

Старый скорер писал `score: Decimal` в каждый элемент. Это удалено, и не
ради экономии.

Ранжирование — свойство **последовательности**, а не рынка. Материализованный
`score` живёт в данных, переживает свою сортировку и читается следующим
разработчиком как характеристика рынка: его сравнивают, сохраняют,
передают дальше — хотя он был лишь кэшем одного решения сортировки. Ни
`Market`, ни `MarketDiscoveryEntry` такого поля не получают.

## Почему нет часов

`rank()` не принимает `IClock`. Порядок определяется сравнением полей
записей между собой, а не расстоянием до «сейчас»: любая монотонная функция
от `now` дала бы ровно тот же порядок, зато сделала бы результат
невоспроизводимым.

## Разные валюты ликвидности

При совпадающих валютах — по сумме DESC. При разных — по коду валюты ASC,
то есть записи группируются по валюте, а суммы сравниваются внутри группы.

Соблазнительный вариант «разные валюты → ничья, падаем на identity»
**нетранзитивен**: легко строится цикл `B < A < C < B`, а массив с
циклическим компаратором сортируется недетерминированно — ровно то, против
чего заведён identity-хвост. Лексикографический порядок `(валюта, −сумма)`
транзитивен по построению, не выдумывает курс и не бросает исключений
(падать на ранжировании нельзя).

На практике ветка почти недостижима: discovery отдаёт USDC, отсутствующее
значение — `Money.of(0, 'USDC')`. Она существует, чтобы отсутствие
FX-политики было явным, а не подразумеваемым.
