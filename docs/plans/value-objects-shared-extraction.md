**Итог по коммитам:** `3e7fa4c0` (шаг сетки), `4578d9ea` (скаляр),

Критерий неизменности поведения выдержан: в этапах 3 и 4 НИ ОДИН тест не

## Почему это делается

Аудит пакета `@polymarket/value-objects` (15 доменов, ~29 300 LOC) показал
три семейства клонов. Ценность не в сокращении строк — она в том, что
копии **расходятся**, и расхождение оказывается дефектом: из девяти копий
`safeStringify` верной была одна, из двух реализаций проверки выравнивания
жили обе. Одна реализация не может разойтись сама с собой.

## Этап 2: `ValidateGridStep` — шаг дискретной сетки

### Факты

`ValidateStepSizeForQuantity` и `ValidateStepSizeForSignedQuantity`
идентичны: diff показывает только тип ошибки и наличие поля `reason`.
Оба — строгое ПОДМНОЖЕСТВО `ValidateTickSize`:

| проверка | StepSize | TickSize |
|---|---|---|
| `isNaN` | нет (ловится через `isFinite`) | есть, свой reason |
| `isFinite` | есть | есть |
| `<= 0` | есть | есть |
| `> maxAllowed` | нет | есть, опционально |

У `ValidateStepSizeForQuantity` в контексте ошибки **нет `reason` вообще** —
потребитель не может отличить «не конечный» от «не положительный». У
signed-версии `reason` есть. Это расхождение копий, а не решение.

### Проблема размещения

Тик сейчас в `shared/price/`, но шаг нужен `quantity`, который ценовым
доменом не является. Значит понятие живёт выше обоих: «шаг дискретной
сетки» общий для цен и количеств. Класть его в `shared/price/` —
повторить ошибку плоской папки, из-за которой `shared/` уже пришлось
разбирать.

### Действия

1. Создать `shared/numeric/ValidateGridStep.ts` — обобщённое правило по
   образцу `ValidateAligned`: принимает `ErrorConstructor` домена и
   необязательный `maxAllowed`.
2. `shared/price/ValidateTickSize` → делегирует ему (тик = шаг с максимумом).
3. `quantity/rules/ValidateStepSizeForQuantity` и signed-версия →
   делегируют ему; обе получают `reason` из общего словаря.
4. Завести `shared/numeric/NumericRuleReason` по образцу `PriceRuleReason`
   либо переиспользовать его, если пересечение полное.

### Риск

Низкий. 4 места вызова, все внутри пакета, потребителей снаружи нет.

### Результат (выполнено)

Оба step-правила и `ValidateTickSize` делегируют `validateGridStep`.
Попутно вскрылись два дефекта того же класса, что и мёртвые члены у цен:

1. У `QuantityErrorReason` член `INVALID_STEP_SIZE` существовал, но не
   эмитился НИКОГДА — правило вовсе не клало `reason` в контекст. Теперь
   член ожил. (`DIVISION_BY_ZERO` там же остаётся мёртвым — отдельная
   уборка.)
2. Оба step-правила не имели ветки для `NaN`: он проваливался в проверку
   `isFinite` и приходил как «не конечный», неотличимый от `Infinity`.
   Тесты пиннили именно это поведение — то есть закрепляли дефект.
   Исправлено, ожидания обновлены с объяснением.

## Этап 3: `quantity` / `signed-quantity` → общий скаляр

### Факты

Перекрытие фасадов — 7 методов: `create`, `add`, `subtract`, `multiply`,
`divide`, `roundToStep`, `portion`. У `Quantity` их всего 8, у
`SignedQuantity` — 11 (сверх общих: `abs`, `negate`, `scale`, `adjustBy`).

Инварианты вложены: `Quantity` = NaN + finite + **неотрицательное**,
`SignedQuantity` = NaN + finite. То есть `Quantity` строже, а не «другой».

### Действия

1. Обобщить контракт: `DecimalPrice` (в `shared/price/`) на деле не знает
   ничего о цене — это `{ value(): Decimal }`. Переносится в
   `shared/numeric/DecimalValue.ts`, `DecimalPrice` остаётся алиасом ради
   совместимости импортов.
2. `shared/numeric/scalarDomain.ts` — дескриптор по образцу `PriceDomain`
   (фабрика + тип ошибки + имя сервиса).
3. `shared/numeric/scalarOperations.ts` — семь общих операций.
4. Фасады делегируют; доменное (`abs`/`negate`/`complement`) остаётся дома.

### Чего НЕ делать

Не заводить общий класс-предок. Как и с ценами: общий предок размыл бы
инварианты (`Quantity` не может быть отрицательным, `SignedQuantity`
может) и сломал бы `equals` — два значения из разных доменов сравнивались
бы как равные.

## Этап 4: `balance` / `token-balance`

### Факты и ограничение

Файловая структура совпадает с точностью до двух файлов. Но ядра
параллельны НЕ полностью:

```text
Balance      (available: Money,     reserved: Money,     accountId, venueId)
TokenBalance (token: OutcomeToken, available: Quantity, reserved: Quantity,
              accountId, venueId)
```

У `Balance` идентичность актива живёт ВНУТРИ `Money` (валюта), у
`TokenBalance` — отдельным полем. Параметризовать «по типу актива» в лоб
нельзя: у одного четыре поля, у другого пять.

### Что реально общее

Арифметика резервирования. `ValidateReserveAmount` в двух доменах
совпадает построчно — diff только `reserveAmount`↔`reserveQty` и имя
члена reason (`INSUFFICIENT_FUNDS` против `INSUFFICIENT_AVAILABLE`). То же
у `ValidateReleaseAmount`. Методы `reserve`, `unfreezeReserved`,
`consumeReserved`, `updateAvailable` — один алгоритм: проверить величину,
вычесть из available, прибавить к reserved.

### Действия

1. `shared/reservable/` — правила и операции над парой
   `(available, reserved)`, параметризованные типом величины и
   `ErrorConstructor` домена.
2. Идентичность актива остаётся в домене: `ValidateCurrencyMatch` и
   `ValidateTokenMatch` НЕ сводятся — у первого валюта берётся из значения,
   у второго токен приходит отдельно.
3. Ядра (`Balance`, `TokenBalance`) не трогать: разница в форме честная.

### Риск

Наивысший из трёх этапов: 22 файла тестов. Делать последним и отдельным
коммитом, чтобы откат не задевал этапы 2–3.

## Отдельно: `ctx` до `wrapOp` — НЕ в этом MR

45 мест в 10 фасадах строят контекст ошибки из параметров ДО входа в
`wrapOp`:

```ts
const ctx = { available: balance.available().value().toString(), ... };
return wrapOp(SERVICE_NAME, op, ctx, () => { ... });
```

Это тот же класс дефекта, который был исправлен в `FeeSerializer`:
аргументы вычисляются раньше, чем начинает действовать защита. Показательно,
что `TokenBalanceService` в том же месте защищается `?.`, а
`BalanceService` — нет; то есть автор второго об этом знал, а первого нет.

**Severity здесь ниже**, чем у сериализатора: параметры типизированы, это
внутренний API, а не граница доверия — сериализатор существует ровно для
того, чтобы принимать непроверенные данные, а фасад нет. Поэтому чинится
отдельно и с отдельным решением: либо ленивый контекст в `wrapOp`, либо
гард на входе каждого метода.
