# Комиссия Polymarket: чем она удерживается

Документ фиксирует **измеренный** механизм удержания комиссии. Он понадобился,
потому что в репозитории одновременно жили две несовместимые модели, каждая со
своими проходящими тестами, и выбрать между ними рассуждением было нельзя.

## Правило

Комиссию платит **только тейкер**, платит её **деньгами**, и платит **из того,
что получает**. Количество токенов не изменяется никогда.

```text
BUY  тейкер   отдаём  номинал + fee    получаем ПОЛНЫЕ size шар
SELL тейкер   получаем номинал − fee   отдаём  ПОЛНЫЕ size шар
мейкер        ровно номинал            комиссии нет
```

Ставка — документированная формула площадки:

```text
fee = size × feeRate × p × (1 − p)      feeRate = 0.07 для crypto-рынков
```

## Как это измерено

Публичная лента активности (`listActivity`) отдаёт по каждой сделке `shares`,
`price` и `amount` — фактически перемещённый USDC. Комиссия равна **модулю**
расхождения `shares × price` с `amount`; знак говорит лишь о стороне.

Роль maker/taker лента не отдаёт — таких полей в записи нет. Она и не нужна: у
мейкерского фила расхождение нулевое.

Замер по всей истории кошелька, 2898 сделок:

| сторона | сделок | расхождение = 0 | расхождение ≠ 0 |
| --- | --- | --- | --- |
| BUY | 1888 | 1857 | 31, все отрицательные |
| SELL | 1010 | 732 | 278, все положительные |

Отрицательных расхождений по SELL и положительных по BUY нет ни одного —
знак строго определяется стороной.

Совпадение с формулой точное:

```text
size 20, p 0.50   fee 0.35000    20 × 0.07 × 0.50 × 0.50 = 0.35000
size 20, p 0.38   fee 0.32984    20 × 0.07 × 0.38 × 0.62 = 0.32984
size 20, p 0.17   fee 0.19754    20 × 0.07 × 0.17 × 0.83 = 0.19754
size  5, p 0.47   fee 0.08718     5 × 0.07 × 0.47 × 0.53 = 0.087185
```

Нули — мейкерские филы, а не отсутствие комиссии как явления.

## Что это опровергает

Расчёт вида `feeInTokens = feeUSDC / price` с ростом позиции на
`size − feeInTokens` описывает механизм, **которого не существует**. Ни одна из
1888 покупок не показала уменьшенного количества шар.

Модель дожила до сегодня потому, что её тест и тест правильной модели проверяют
разные вещи и нигде не встречаются.

## Где правило выражено в коде

Экономику исполнения несёт сам `Fill` — пересчитывать её потребителю не нужно
и вредно:

```typescript
fill.getSignedQuantity();  // ±size, ВАЛОВОЕ количество
fill.getCashFlow();        // ∓(price × size), без комиссии
fill.getFeeFlow();         // −fee, всегда в settlement-активе
fill.getNetCashFlow();     // cashFlow + feeFlow — деньги с учётом комиссии
```

`getNetCashFlow()` верен для обеих сторон: на покупке даёт
`−(номинал + fee)`, на продаже `+(номинал − fee)`.

Инвариант `Fill`, требующий `fee.asset === settlementAssetId` при ненулевой
комиссии, — прямое следствие правила и **не** случайное ограничение.

## Состояние потребителей

| место | вердикт |
| --- | --- |
| `Fill.getNetCashFlow` / `getSignedQuantity` | верно |
| `FillMapper` — мейкеру `fee = 0` | верно |
| `apps/pnl` | верно после правки измерения |
| `PortfolioService` | исправлен: комиссия деньгами, количество валовое |
| `Portfolio.applyFill` (агрегат) | исправлен: применяет `getNetCashFlow()` |

### Что было не так в `PortfolioService`

Позиция росла на `size − feeUSDC / price`, а деньги двигались ровно на номинал.
Исправлено:

```text
BUY   номинал из reserved + комиссия из available    позиция +ПОЛНЫЙ size
SELL  зачисляем номинал − комиссию                   позиция −ПОЛНЫЙ size
```

Комиссия на покупке снимается отдельным шагом из `available`, потому что её
никто не резервировал: в момент размещения ордера ещё неизвестно, окажемся мы
тейкером или мейкером. `reverseFill()` зеркалит это же.

Правку пришлось начать с фикстур: оба теста подсовывали структурные заглушки
вместо `Fill`, причём одна из них САМА подделывала `getNetCashFlow()` — жёстко
зашитые `-32.5` и голый `Decimal` вместо `SignedQuantity`. Пока сервис
экономику пересчитывал сам, подделка держалась. Применить математику домена
можно только с объектами домена.

### Что было не так в `apps/pnl`

Измерение стояло с клампом `Math.max(0, shares × price − amount)`. На покупке
расхождение отрицательно, поэтому кламп обнулял **всю** покупательскую
сторону: 31 тейкерская покупка и 2.92 USDC комиссий не попадали в отчёт.
Исправлено взятием модуля.
