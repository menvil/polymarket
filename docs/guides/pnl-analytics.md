# PnL-аналитика (`apps/pnl`)

Read-only CLI: сколько мы заработали или потеряли на Polymarket за период.

```bash
# Краткая сводка по дням
npm run start -w @polymarket/pnl -- --from 2026-08-01 --to 2026-08-31

# Подробный отчёт: блок на день → сделки по каждому рынку
npm run start -w @polymarket/pnl -- --from 2026-09-08 --mode detailed

# JSON для дальнейшей обработки
npm run start -w @polymarket/pnl -- --from 2026-08-01 --json

# Включить ещё не закрытые позиции
npm run start -w @polymarket/pnl -- --from 2026-08-01 --include-open
```

Конфиг — `apps/pnl/.env`, шаблон рядом в `.env.example`. Обязателен один
`WALLET_ADDRESS`; остальное — только за комиссиями.

> `--` перед флагами обязателен: без него npm съест их сам, а не передаст
> скрипту.

В машинных режимах (`--json`, `--raw`) логи приглушены до ошибок: логгер
пишет через `console.log`, то есть в stdout, и вперемешку с JSON его нечем
разобрать. Пустой период в `--json` тоже отдаёт отчёт установленной формы с
нулями, а не прозу.

Обязателен один параметр окружения — `WALLET_ADDRESS` (или `FUNDER_ADDRESS`).

## Два пути, и второй включается сам

| | публичный | аутентифицированный |
| --- | --- | --- |
| что нужно в окружении | только адрес | + `PRIVATE_KEY`, `POLYMARKET_API_KEY/SECRET/PASSPHRASE` |
| источник сделок | `listActivity()` | `listAccountTrades()` |
| комиссия по fill | `—` | есть |
| роль MAKER/TAKER | `TAKER` по умолчанию | настоящая |
| разбор sub-maker сделок | не нужен | делается |

Путь выбирается **по наличию креденшелов**: есть все четыре — идём
аутентифицированным, нет — публичным. Отчёт строится в обоих случаях,
отличается только детализация.

```bash
# публичный: достаточно WALLET_ADDRESS в apps/pnl/.env
npm run start -w @polymarket/pnl -- --from 2026-06-01

# разово, вообще без файла конфигурации
WALLET_ADDRESS=0x… npx tsx apps/pnl/src/main.ts --from 2026-06-01

# аутентифицированный: взять готовые креды из другого .env
npx tsx --env-file=apps/bot/.env apps/pnl/src/main.ts --from 2026-06-01 --mode detailed
```

## Почему публичный путь вообще существует

Прежняя версия ТРЕБОВАЛА `PRIVATE_KEY` — ключ, способный подписывать
ордера, — ради таблицы в терминале. Теперь он опционален: нужен только за
комиссиями.

Позиции и активность на Polymarket **публичны**. `createPublicClient()`
из официального SDK читает их по адресу кошелька без единого секрета:

```typescript
const client = createPublicClient();       // никаких креденшелов
await client.listActivity({ user, start, end, type: [ActivityType.TRADE] });
await client.listClosedPositions({ user });
```

Проверено: `createSecureClient` требует **настоящий** signer даже когда
готовые `credentials` переданы — он всё равно зовёт `getAddress` +
`signTypedData` и идёт в `/auth/api-key`. Поэтому «читать без ключей»
возможно только на публичном пути, и мы на нём.

## Откуда берётся число

```text
netPnl  = realizedPnl позиции          ← считает площадка
entryCost    = avgPrice × totalBought  ← из позиции
sellProceeds = Σ SELL.amount           ← из ленты сделок
netShares    = Σ BUY.shares − Σ SELL.shares
redeemValue  = netShares × curPrice    ← 0.0 или 1.0 после резолюции
roi          = netPnl / entryCost
```

`netPnl` **не пересчитывается** — это `realizedPnl` площадки, ровно то
число, что показывает сайт.

> **Разбивка не обязана сходиться до цента.** `Entry` и `Sold` считаются по
> сделкам внутри запрошенного периода, а `realizedPnl` — по всей истории
> позиции. Если вход был раньше начала окна, `Sold − Entry` разойдётся с
> `Net PnL`. Разбивка **объясняет** число, а не воспроизводит его.

### Комиссии — измерение, а не модель

**Публичный путь берёт фактически удержанную сумму.** Лента отдаёт `amount` —
реально перемещённый USDC, уже за вычетом комиссии:

```text
fee = shares × price − amount
```

Проверено на боевых сделках: SELL 5 @ 0.47 → `shares × price` = 2.35000,
`amount` = 2.26282, комиссия **0.08718**. Документированная формула даёт
0.087185 — совпадение до пятого знака. BUY даёт разницу ровно 0.

Аутентифицированный путь `amount` не отдаёт, поэтому там работает формула
площадки ([docs.polymarket.com/trading/fees](https://docs.polymarket.com/trading/fees)):

```text
fee = size × 0.07 × price × (1 − price)     // только TAKER, в USDC
```

Ставку **нельзя** брать из ответов API:

| поле | значение | почему не годится |
| --- | --- | --- |
| `feeRateBps` в сделке | `"0"` | не заполняется |
| `taker_base_fee` рынка | `1000` | ≠ замеру (0.07) |
| `maker_base_fee` рынка | `1000` | мейкер не платит вовсе |

Агрегация строгая: комиссия рынка известна, только если известна у
**каждого** fill; достаточно одного неизвестного, чтобы итог стал `—`.
Частичная сумма, выданная за полную, хуже честного прочерка.

> Ставка `0.07` — из документации, подтверждена измерением. В коде проекта
> стояло `0.072`: завышало комиссию на 2.9%. Исправлено в
> `packages/domain/entities/fill/src/polymarket-fee.ts`.

## Устройство

| файл | назначение |
| --- | --- |
| `main.ts` | оркестрация: activity → positions → calculate → render |
| `PnlConfig.ts` | CLI-аргументы и `WALLET_ADDRESS` |
| `core/ActivityFetcher.ts` | публичный путь: сделки из `listActivity()`, фильтр `type` на сервере |
| `core/TradesFetcher.ts` | аутентифицированный путь: `listAccountTrades()` со ставками комиссий |
| `core/EthersSigner.ts` | `Signer` для SDK поверх ethers v6 (SDK везёт адаптеры только для v5 и viem) |
| `core/PositionsFetcher.ts` | позиции с `realizedPnl` из `listClosedPositions()` |
| `core/PnlCalculator.ts` | агрегация по рынкам и дням |
| `renderers/` | краткая и подробная таблицы, `fmtOptional` для `—` |
| `types.ts` | типы отчёта; wire-формат держит SDK |

Две особенности API, на которые опирается код:

- **Combo-сделки отбрасываются.** `listActivity` отдаёт и их (`isCombo: true`),
  но они торгуют позицию протокола v2, а не outcome-токен рынка.
- **Период фильтруется у нас.** Ни `listClosedPositions`, ни `listPositions`
  не принимают границы времени — отбор по `timestamp` идёт после загрузки.
- **`curPrice` полиморфен**: у открытой позиции это рыночная цена в (0, 1),
  у закрытой — выплата, ровно 1 или 0. Одним типом не описывается, поэтому в
  отчёте это `PositionValuation`:

  ```typescript
  type PositionValuation =
    | { state: 'OPEN';    price: OutcomePrice }   // живая котировка
    | { state: 'SETTLED'; won: boolean };          // исход, не цена
  ```

  Новый примитив для «цены расчёта» **не заводился**: выплата 1.0/0.0 —
  следствие того, кто выиграл, а не самостоятельная величина. Домен
  моделирует резолюцию так же: `finalization.winning` в архиве несёт
  identity победителя и провенанс, но не цену.
- **`Page` — это `{items, hasMore, nextCursor}`**, не `{data}`.
- **Рынок относится ко дню ЗАКРЫТИЯ**, а не первого входа: PnL реализуется на
  выходе или резолюции. Если момента закрытия нет (открытая позиция), берётся
  последняя сделка; если нет и её — рынок не попадает в дневную разбивку, но
  остаётся в итоговых суммах.
- **Средняя цена взвешена по объёму.** Сделка на 0.78 токена не весит столько
  же, сколько на 4.22.
- **`Entry`/`Sold` не показывают равенства**: стоимость входа приходит из
  позиции за всю её историю, а `shares`/`avg` считаются по сделкам внутри
  окна; выручка к тому же уже за вычетом комиссии.
- **`Activity` — размеченное объединение**: поля сделки есть только у
  варианта `TRADE`, и сузить надо ещё по `isCombo`.

## Value Objects, а не сырые числа

Раньше здесь стояло обоснование «read-only аналитика, VO добавили бы церемонию
без выгоды». Практика его опровергла: за одну сессию сырые числа дали четыре
ошибки размерности, и самая дорогая печатала **ROI в 100 раз меньше** — −6.0%
выглядели как −0.1%.

Отчёт не защищён от таких ошибок тем, что он read-only: заниженный ROI приводит
к неверному решению так же надёжно, как неверный ордер, только увидеть это
труднее.

| величина | тип |
| --- | --- |
| суммы в USDC | `Money` |
| цена сделки | `OutcomePrice` |
| количество токенов | `Quantity` |
| доходность | `Ratio` |
| оценка позиции | `PositionValuation` — размеченное объединение |
| моменты времени | `Timestamp` |
| нетто-остаток токенов | `SignedQuantity` — знаковый |
| счётчики (`wins`, `losses`) | `number` — безразмерны |

Арифметика идёт через `*Service`; `Decimal` приложение не импортирует вовсе.
Всё разворачивание `Result` собрано в `core/vo.ts` — величина уже прошла
инварианты при создании, поэтому отказ означает дефект, а не исход.

Форматирование — обёртки над `MoneyFormatter`/`RatioFormatter`. Своего у нас
осталось только то, чего они не умеют: ведущий `+`, выравнивание по ширине и
прочерк для недоступных величин. См. ADR, Решение 14.
