# Аудит закалки, потерянной при переезде на V2

Ревью legacy-контура сбора на предмет решений, которые были найдены дорогой
ценой и потерялись при миграции. Повод — дефект, найденный прогоном
[run-02](collector-qualification-run-02.md): RTDS Polymarket умирал молча, и
выяснилось, что **в V1 защита от этого была**, причём тщательнее нашей.

## Почему такой аудит вообще нужен

Закалка редко живёт в коде как требование. Она живёт как условие в `if`,
как строчка в `finally`, как константа с комментарием — и переписывание
слоя её не сохраняет, потому что переписывают функциональность, а не список
однажды случившихся аварий.

Признак, по которому такие места находятся: **коммит-сага**. Один фикс,
второй фикс поверх, откат посередине — значит, тему изучали дорого.

## Метод

1. Инвентаризация удалённого: `git log --diff-filter=D` по путям сбора.
2. Поиск коммитов-закалок: `--grep=fix` по тем же путям; особое внимание
   парам «fix → revert → fix».
3. Для каждого механизма — сверка «есть ли эквивалент в V2».
4. Проверка находок на живом прогоне, где это возможно.

## Находки

### 1. RTDS: детектор живости и двухуровневая эскалация — БЫЛО И ПОТЕРЯНО

Legacy `RtdsWebSocketClient` (удалён при переходе на официальный SDK):

```text
staleMs                 30 000
staleCheckIntervalMs     5 000
PING heartbeat
auto-reconnect           1s → 30s exponential backoff
кэш подписок для восстановления после reconnect
эскалация: stale → resubscribe topic
           stale СНОВА → _forceReconnect('subscription_stale_after_resubscribe')
cooldown resubscribe по топику
```

Дефект был **внесён миграцией**: самописный WS-клиент со сторожем заменили
на SDK, чей `subscribe()` отдаёт async-итератор, который просто заканчивается.
Живучесть при этом никто не перенёс — она выпала вместе с транспортом.

**Статус: восстановлено** — см. [надзор за живостью RTDS](rtds-liveness-supervision.md).
Первый уровень закрыт в PR #87, второй — коммитом `4e0b0a98`.

### 2. CCXT: кэши брошенного инстанса не освобождались — ПОТЕРЯНО

Legacy освобождал их явно:

```typescript
private _clearClosedInstanceState(instance) {
  for (const prop of ['trades', 'orderbooks', 'myTrades', 'orders']) {
    this._clearCacheObject(instance?.[prop]);
  }
}
```

Тема изучалась дорого — сага из трёх коммитов:

```text
bd8b7db5  eliminate ccxt.pro memory accumulation causing OOM
a665f489  clear ccxt.pro ArrayCache in-place after writing to disk
d47fb7f6  revert ccxt.pro trades cache reset — ArrayCache not a plain array
```

Откат в середине — та самая метка «здесь есть неочевидность»:
`instance.trades[symbol]` наследует `Array` и имеет собственный `append`,
поэтому очищать надо `.length = 0`, а **замена ссылки ломает vendor-код**.

V2 закрывает WS-клиенты и инстанс, но кэши не трогает. Складывается плохо с
другой его особенностью: закрытие инстанса — fire-and-forget с таймаутом,
и код прямо документирует, что `instance.close()` может зависнуть. Зависшее
закрытие → инстанс жив → его стаканы живы. При плановом рестарте раз в
15 минут это 96 поколений на биржу в сутки.

Косвенное подтверждение: run-02 держал RSS до 976 МБ против коридора
308–704 МБ в run-01.

**Статус: восстановлено**, с одним отличием от legacy. Legacy чистил в
`.finally()` операции закрытия — для нас этого мало: интересующий случай
именно ЗАВИСШЕЕ закрытие, а у зависшего промиса `finally` не выполнится
никогда. Поэтому освобождение привязано к моменту «мы перестали ждать»
(истёк `closeTimeoutMs`), и повторно — по фактическому settle.

Осознанно **не** восстановлена очистка кэша во время работы: V2 создаёт
инстансы с `newUpdates: true`, повторной эмиссии нет, объём ограничен
`tradesLimit` и плановым рестартом. Это задокументированное решение, а не
упущение.

### 3. Ранний выход из settlement grace — ПОТЕРЯНО, чинить не нужно

Legacy имел порт `CollectionSettlementObserver`: «пришло ли наблюдение с
vendor-timestamp не раньше границы» → выйти из grace досрочно. V2 всегда
высиживает полные 5 секунд (слайсами — только чтобы `close()` прерывался).

**Оговорка, которая меняет вывод:** порт был опциональным, и единственное
его использование вне самого координатора нашлось в тесте. Похоже, в
production он никогда не подключался. Это скорее нереализованная идея, чем
работавшая закалка, а выигрыш — единицы секунд на рынок.

**Статус: не восстанавливаем осознанно.**

## Проверено и на месте

Чтобы аудит не выглядел списком одних потерь — вот что перенесено
добросовестно:

| механизм | legacy | V2 |
| --- | --- | --- |
| `RestartingTask` с cooldown | есть | есть |
| stale-таймаут watch-вызовов (60 с стакан / 180 с сделки) | есть | есть |
| детекция crossed book (`ask < bid`) | есть | есть |
| плановый рестарт инстансов | есть | есть |
| `SPOT_DEPTH_WHITELIST` (bybit, coinbase) | есть | есть |
| keep-alive overrides ccxt.pro | **нет** | есть |
| архивы: tmp+rename, fsync/drain, таймауты | частично | сильнее |
| приём `price_change` / `tick_size_change` | выбрасывал | пишет сырым |
| DNS override (DoH) | есть | есть, вынесен в пакет |

Два последних пункта — случаи, где **V2 лучше**: legacy явно отбрасывал
`price_change`, а V2 сохраняет весь сырой поток.

## Открытые вопросы без действия

**PING heartbeat RTDS.** У legacy был свой. V2 полагается на SDK, а тот
держит ping внутри: в публичных `.d.ts` его нет, настроить нельзя.
Доказательство, что это не теория: в run-02 все шесть фидов молчали 32
секунды при нуле ошибок — транспортный уровень SDK отказа не заметил.

Отсюда практический вывод: **watchdog по данным — не подстраховка, а
единственный детектор.** Это аргумент за низкий порог и против того, чтобы
его когда-нибудь ослабить.

**Ретраи Gamma.** Legacy REST различал 4xx (не ретраить) и 5xx с
экспоненциальным backoff. V2 ретраит однородно раз в 30 секунд до часа: на
постоянном 4xx это ~120 лишних вызовов на рынок. Неэффективность, не потеря
корректности.

## Что НЕ проверялось

Только контур сбора. Стратегии, бот и исполнение ордеров не смотрел — если
там есть своя legacy-закалка, это отдельный заход.
