# ADR: Контракт границы примитив/VO для packages/domain + packages/application

**Статус:** Принято
**Дата:** 2026-08-04
**Контекст:** Этап 0 плана миграции `packages/domain` + `packages/application` на строгую
типизацию через value-objects/branded-ID/Result (`/Users/menvil/.claude/plans/synthetic-swimming-heron.md`).

---

## Контекст

Пакеты `domain/*` и `application/*` соблюдают эталонный контракт (`@polymarket/value-objects`,
`@polymarket/result`, `@polymarket/errors`, `@polymarket/ids`) неравномерно — это
подтверждено дважды независимо (механический построчный скан + ручное исследование).
Три системных расхождения:

1. Примитивы (`Decimal`/`number`/`string`) на публичных границах там, где есть готовый
   VO/branded ID.
2. `throw` вместо `Result<T, E>` вне `value-objects`.
3. Дублирование модели стакана (`@polymarket/orderbook` vs `@polymarket/order-book`) —
   закрывается отдельно, Этап 2 плана, не предмет этого ADR.

Дополнительно вскрылось: часть уже построенных VO/entities (`Position`, `Trade`,
`Ledger` read-API, 8 из 14 facade-слоёв VO) **не используются вообще** — проблема не
только «заменить примитив на VO», но и «начать вызывать то, что уже написано».

Этот документ фиксирует единый контракт как источник истины для всех последующих этапов
миграции (Этапы 1-11) — они на него ссылаются, а не переизобретают правило по месту.

---

## Решения

### 1. Граница примитив/VO

**Решение:** Примитивы (`Decimal`/`number`/`string`) легитимны **только на границах
системы**: JSON-DTO, персистентный снапшот (то, что реально лежит в БД/файле/journal),
лог/сообщение об ошибке, конфигурация, внутренняя реализация самого VO. Внутри доменных
сценариев (domain-модель, публичный API пакета, порт приложения) значения с доменным
смыслом (деньги, цена, количество, resolved identity, момент времени) обязаны быть VO
или branded ID.

**Обоснование:** Не любой примитив — долг. `string` для `MarketQuestion`/
`CancellationReason` не нуждается в VO (нет собственного инварианта или поведения —
завести класс ради класса значит породить архитектурный мусор). `.value().toString()`
в логе — не нарушение (десятки легитимных мест, например весь `PlaceOrderUseCase.ts`
логирует величины через `.toString()`). Нарушение — это когда значение с доменным
смыслом **вычисляется или сравнивается** как примитив там, где должен быть VO
(`price.value().times(size.value())` вместо cross-VO helper, `fill.side === 'BUY'`
там, где ценность несёт не сравнение, а `SideService.opposite()`/`canMatch()`).

**Контракт (правило для ESLint, Этап 0.4 / Решение 6 ниже):**

```
Запрещено вне {packages/domain/value-objects, packages/foundation/math}:
  import Decimal from 'decimal.js'
  + любая арифметика (.times/.plus/.minus/.div и т.п.) над извлечённым значением

Разрешено везде:
  .value().toString() / .value().toNumber() — сериализация в лог/DTO/сообщение об ошибке
```

Не бланкетный запрет `.value(): Decimal` — он дал бы ложные срабатывания на легитимных
местах и правило бы отключили.

### 2. Facade-слой для новых VO-операций — не копировать бездумно

**Решение:** Новые VO-операции (Этапы 1-9 плана) размещаются по критерию **тотальности**,
а не автоматически в `XxxService` facade:
- Тотальная операция над уже валидными экземплярами (не может провалиться содержательно) →
  core, plain-возврат. Пример-эталон — `SignedQuantity` (`add/subtract/compare/sign/abs/neg`
  все в core, все plain-возвраты).
- Частичная операция, где провал — бизнес-исход (`Balance.reserve` при недостатке
  средств) → core, но возвращает `Result`.
- Частичная операция, где провал — кривой внешний вход (`MoneyService.create(raw)`) или
  нужна policy (`PriceService.roundToMarketTick`) → facade, `Result`.
- Невозможное состояние → throw (только внутри value-objects).

**Обоснование:** Проверено прямым grep: 8 из 14 facade-сабмодулей VO (`MoneyService`,
`QuoteService`, `RatioService`, `TokenBalanceService`, `SideService`, `OutcomeTokenService`,
`FeeService`, `AssetQuantityService`) — **0 внешних вызовов**. Прикладной код либо зовёт
`Money.of()` напрямую (throw-API), либо считает на голом `Decimal`, мимо VO вообще —
в обе стороны мимо facade. Паттерн «спрятать всё в Service» уже показал, что его
игнорируют; копировать его для новых VO-операций значит повторить ту же ошибку.

### 3. Duration — новый VO не заводится

**Решение:** Для длительностей (`timeToExpiryMs`, `leaseMs`, `staleMs`,
`maxCrossVenueSkewMs`, `persistenceMs` и т.п.) отдельный класс/VO **не создаётся**.

**Обоснование:** `Timestamp` уже имеет `addMs(delta: Decimal): Timestamp` и
`diffMs`/`diffSeconds(other): Decimal` (core, `timestamp/core/Timestamp.ts:367,402,420`,
дублируется в facade `TimestampService`) — вся арифметика «точка времени ± длительность»
и «разница между двумя точками» уже закрыта. Отдельный класс здесь противоречил бы
собственному принципу «расширяем существующие модули, новых VO не заводим без крайней
нужды» (тот же принцип, по которому не заводится VO для `MarketQuestion`, Решение 1).

**Контракт:**
```
Длительность = разница двух Timestamp → Timestamp.diffMs / TimestampService.diffMs
               (не ручное a.toNumber() - b.toNumber())
Длительность = самостоятельный конфиг/порог (не производная двух Timestamp)
               → остаётся number(ms), это легитимный примитив без собственного инварианта
```

### 4. Orphaned сущности: реюз, а не удаление

**Решение:** Три сущности построены с полным соблюдением контракта, но не подключены —
для каждой принято решение (не «зафиксировать и забыть»):

| Сущность | Решение | Этап плана |
|---|---|---|
| `Position` (lot-based FIFO/LIFO) | Подключена в `PortfolioService._applyPositionUpdate` (не `Portfolio.applyFill` — такого метода не существует, ошибка в исходном тексте этого ADR) | Этап 3 |
| `Trade` + `ExecutionLinker` | Строить сейчас — `TradeMapper.fromPolymarketLastTradeEvent()` уже реализован, нужно только подключить (`MarketDataStore` TRADE_RECEIVED-обработчик + новый `ExecutionLinker`) | Этапы 2, 7 |
| `Ledger` read/replay API | Подключить реального потребителя (`LedgerService.ts`, reconciliation-сценарий) | Этап 7 |

**Обоснование:** `Portfolio` использует `SimplePosition` явно «без зависимости от
@polymarket/position» (`SimplePosition.ts:8`) — это не архитектурный дубль, а реальный
functional gap (PnL при частичном закрытии позиции без честного FIFO/LIFO).
`Fill.venueTradeId` спроектирован под связь с `Trade`, но `ExecutionLinker` не существует
нигде в коде. `Ledger` пишется (`.append()`), но не читается никем.

**Пересмотр валидационной стратегии для Position (при реализации Этапа 3):** исходная
формулировка этого ADR ("детерминированный shadow-compare гейт, полный исторический
бэктест-корпус, точное равенство Decimal") предполагала сравнение realized+unrealized PnL
между `SimplePosition`-путём и lot-based путём. Расследование при реализации показало:
production fill-путь (`PortfolioService._applyPositionUpdate`, до Этапа 3) **вообще не
вычислял** realized PnL — не приблизительно, а буквально нигде не накапливал такое число.
Сравнивать lot-based `realizedPnL` было не с чем. Пересмотренная стратегия (см.
`docs/architecture/position-accounting.md`): `quantity` — точное совпадение всегда
(проверяет корректность BUY/SELL/fee-проводки); `averageEntryPrice` — точное совпадение
только для single-price-lot сценариев, **математически ожидаемое расхождение** для
multi-lot partial close (не баг — сама причина, почему lot-based учёт вообще нужен);
`realizedPnL` — новая способность, валидируется выделенными unit-тестами с заранее
известными ожидаемыми значениями, не diff против несуществующего бейзлайна.

### 5. Deprecation-мост

**Решение:** Публичные сигнатуры, меняющиеся в рамках миграции и имеющие внешних
потребителей за пределами текущего этапа, получают временный `@deprecated`-мост: новое
API вводится рядом со старым, старое помечается `@deprecated` с указанием замены и этапа
снятия. Мосты снимаются централизованно на Этапе 10 (`grep -rn "@deprecated"` должен дать
пусто, кроме сознательно оставленных и перечисленных в `docs/migration/README.md`).

**Обоснование:** Позволяет каждому этапу быть самостоятельно зелёным (`build && test &&
lint && typecheck`) не дожидаясь, пока смигрируют все потребители сразу — потребители
переходят на новое API внутри СВОЕГО этапа (см. таблицу зависимостей этапов в плане).

### 6. ESLint-стратегия

**Решение:** Правило про `import Decimal from 'decimal.js'` (Решение 1) заводится в
Этапе 0 как `warn` + allowlist (список = `docs/migration/decimal-import-files.txt`,
сгенерирован `scripts/scan-conventions.mjs`). Allowlist сокращается по мере того, как
каждый этап (2,3,4,6,7,8,9) мигрирует свои файлы. Этап 11 снимает allowlist и переводит
правило в `error` без исключений (кроме `value-objects`/`math`), репо-wide, в CI.

**Обоснование:** Включение правила только в конце (после всех 10 этапов) оставляет всю
миграцию без защиты от НОВЫХ нарушений, вводимых по ходу работы — половина смысла
правила теряется. Baseline+shrink+hard-gate защищает с первого дня, не давая долгу расти
там, где он уже сокращается.

### 7. Что осознанно не реализуется в рамках этой миграции

- **UnitOfWork / IKeyedMutex TTL / recoverIncomplete()** — 5 TODO по коду
  (`IOrderStateStore.ts:240`, `IKeyedMutex.ts:48`, `IMarketDataRecorder.ts:131`,
  `ProcessFillUseCase.ts:821-822`, `PlaceOrderUseCase.ts:15,1015`) указывают на одну
  архитектурную проблему — нет транзакционной границы через
  Order+Portfolio+Ledger+ProcessedFill. Это concurrency/consistency-архитектура, другой
  род работы и риска, чем типизация. `docs/architecture/unit-of-work.md` (пишется на
  Этапе 5) — реальный design-документ с конкретным предлагаемым решением, не архив.
  Реализация — **Этап 12, следующий сразу за Этапом 11**, отдельная сессия планирования.
- **`MARKET_OPENED`/`MARKET_CLOSED` без продюсеров** — события уже есть в
  `ApplicationEvent` union (`event-bus/src/events/index.ts:65,66`), но никто их не
  публикует. Миграция не должна ломать эти контракты (сигнатуры трогать можно и нужно
  по правилам выше, публикацию не заводим).
  Реализация продюсеров — вне скоупа этой миграции.
- **Пакеты из `coordination-plan.md`** (`balance-allocator`, `market-lifecycle`,
  `coordinator`, `ReconcileOrdersUseCase`) — не реализуются. Фиксируется только то, что
  миграция не должна закрывать возможность их появления (не переименовывать/не удалять
  точки интеграции без явной причины).

### 8. Market lifecycle throw→Result: ADR приоритетнее pre-ADR package-local обоснования

**Решение:** `Market.close()`/`Market.resolve()` и `MarketState.close()`/`MarketState.resolve()`
(`@polymarket/market`) переведены с throw на `Result` в Этапе 3, несмотря на то, что
`docs/market-entity.md` (написан до этого ADR) содержал явное архитектурное обоснование
throw-поведения: "сигнализирует — ты вызвал метод в неверном состоянии, это баг в коде"
(различение programmer error vs expected failure).

**Обоснование:** Решение 1 этого ADR не делает исключения для "programmer error" —
throw легитимен только внутри `value-objects`, без оговорок. Конкретная, самосогласованная
pre-ADR позиция пакета не отменяет общий контракт, принятый для всей миграции: если бы
каждый пакет мог обосновать свой собственный throw своей локальной логикой, единого
контракта не было бы вообще. Конверсия оказалась полностью inert для прода — на момент
миграции ни один реальный вызывающий код нигде в репозитории не вызывал
`Market.close()`/`Market.resolve()` (только `type`-импорт `Market` как поля данных в
`StrategyScheduler`/`StrategySnapshot`) — нулевой риск сделал решение простым: не
потребовалось взвешивать "ценность строгого contract vs breaking real callers", реальных
callers не было.

**Общий принцип для будущих этапов:** там, где план (Этапы 4-9) встречает похожий
pre-ADR-обоснованный throw в других пакетах — то же правило: ADR имеет приоритет,
если у throw-сайта нет собственного, отдельно принятого исключения в этом документе
(как "static utility class constructor guard" ниже, Решение 1, или конструкторы-invariant
guards в `OrderIdGenerator`, зафиксированные отдельно для Этапа 9).

### 9. Runtime-валидация `unknown` с VO-полями — `instanceof`, не повторная проверка инварианта

**Решение:** Когда `create()`-фабрика валидирует сырой `unknown`-вход с полями, которые
после конверсии стали VO (`Money`/`Quantity`/...), проверка сводится к `value instanceof
<VO>` — **без** повторной ручной проверки инвариантов, которые сам VO уже enforces на
конструкторе (finite/NaN/диапазон). Если у VO есть инвариант, который он **сознательно
не** enforces (например, `Money` разрешает отрицательные суммы — неотрицательность
конкретного лимита остаётся бизнес-правилом вызывающего кода) — эта проверка остаётся
явной, отдельно от `instanceof`.

**Обоснование:** `RiskPolicy.create()` (`@polymarket/risk`, Этап 7) до конверсии полей
`RiskParams` на `Money`/`Quantity` проверяла `Decimal.isDecimal(value)` →
`isNaN()`/`isFinite()` → `isNegative()` вручную для каждого лимита. После конверсии
`maxPositionSize: Quantity` — невалидный экземпляр `Quantity` физически не существует
в runtime (core enforces `>= 0` и finite на конструкторе), поэтому `instanceof Quantity`
уже достаточен: проверка **упрощается**, не усложняется. `maxTotalExposure`/
`maxOrderNotional`/`minAvailableBalance: Money` — `Money` core **сознательно** допускает
отрицательные суммы (не invariant, см. `Money`'s докблок: "Неотрицательность — бизнес-
логика"), поэтому `!value.isNegative()` остаётся отдельной явной проверкой рядом с
`instanceof Money`. `instanceof` на `unknown` никогда не бросает — свойство "`create()`
никогда не throw, все ошибки через `Result`" сохраняется без изменений.

**Общий принцип для будущих этапов:** та же логика применима к любой будущей
`create()`-фабрике, валидирующей `unknown` с VO-полями — не переносить вручную
Decimal-era диапазонные проверки один-в-один, а спросить для каждого поля: "enforces
ли сам VO этот инвариант на конструкторе?" Если да — `instanceof` достаточен. Если
инвариант сознательно не encoded в VO (как неотрицательность `Money`) — явная проверка
остаётся, но ТОЛЬКО эта, не type-проверка (её уже даёт `instanceof`).

### 10. Частотный класс определяет hot-path-vs-VO, не только наличие границы

**Решение:** Публичная граница пакета/класса — необходимое, но не достаточное условие
для конверсии примитива на VO. Дополнительный вопрос, который нужно задавать явно для
каждого числового поля: **с какой частотой оно конструируется/потребляется?**
Per-tick поля (создаются на каждое WS-событие или на каждый шаг реплея бэктеста —
тысячи-миллионы раз за прогон) остаются `number`/`Decimal`, даже если формально
пересекают публичную границу класса. Per-evaluation/per-signal поля (создаются на
порядки реже — раз на стратегическую оценку, раз на сигнал, раз на закрытие рынка) —
легитимные кандидаты на VO.

**Обоснование:** До Этапа 8 этот принцип уже применялся, но неявно и per-инстанс
(`NumericLevel`/`SimpleBook` в `cross-market`, Этап 4; внутренняя арифметика
`TradeFlowCalculator`/`OrderRiskChecker` после распаковки VO, Этапы 2/4/7). Этап 8
(`market-state`) впервые столкнулся с пакетом, где хот-путные и холодные поля
сосуществуют настолько плотно, что черновой план применил одну и ту же логику
"примитив → VO" ко всему пакету скопом — и это не выдержало проверки:
- `CryptoMarketDataStore`'s `price`/`exchangeTsMs`/`receivedTsMs`/`bids`/`asks` — per-tick
  (реплей бэктеста и живой сбор CEX-данных пишут на каждое WS-событие через
  `updatePrice`/`updateCexBook`/`updateCexTrade`) — остаются `number` навсегда, не
  временный пробел. Дополнительно (независимое от частоты основание): `price` — крипто-
  спот-цена произвольного масштаба (~78 000 для BTC), несовместимая с диапазоном `Price`
  VO (`[0.0001, 0.9999]`) — расширяет вывод Этапа 4 про `MarketInfo.priceToBeat`/
  `finalPrice` на новый пакет.
- `CryptoSignalRegistry`'s `CryptoSignalResult.tsMs`/`.quality`/`.confidence` — по частоте
  (per-evaluation, не per-tick) технически подходящие кандидаты на `Timestamp`/`Ratio` —
  но реальные потребители целиком в ещё не пройденном этапе (Этап 9), поэтому отложены не
  по частотному, а по cross-stage основанию (тот же паттерн, что `IDecisionJournal` в
  Этапе 5 и `IBookRegistry` в Этапе 6 — реальные потребители определяют владеющий этап,
  не факт наличия публичной границы). Частота и cross-stage-принадлежность — независимые
  оси, оцениваются раздельно.

**Общий принцип для будущих этапов:** при встрече со смешанным по частоте пакетом — не
применять единое решение ко всему пакету/файлу. Классифицировать по кластерам полей,
для каждого спросить отдельно: (1) частота конструирования, (2) совместимость диапазона
с существующими VO, (3) есть ли реальные потребители в уже пройденных/текущем этапе.
Все три ответа независимы — поле может пройти (3), но не пройти (1)/(2), и наоборот.

### 11. `apps/bot`: composition root получает inline-правки, `strategies/*` — всегда отложено

**Решение:** Внутри `apps/bot`, когда сигнатура пакета, затронутого текущим этапом,
меняется и ломает сборку потребителя, действует не единое правило "apps/bot — Этап 10", а
различие по поддиректории:
- **`apps/bot/main.ts` + `apps/bot/src/bot/*.ts`** (composition root — сборка
  инфраструктуры/стратегий в один граф зависимостей) — получают механическую inline-правку
  В РАМКАХ ТОГО ЖЕ этапа, что изменил сигнатуру. Не откладывается до Этапа 10.
- **`apps/bot/src/strategies/*`** (конкретные реализации `IStrategy`, ~20 файлов) —
  ВСЕГДА откладывается до Этапа 10, независимо от размера правки (даже 1-3 файла).

**Обоснование:** Composition-root файлы получают уже готовые значения через код текущего
этапа (пример вызова, не бизнес-логика) — правка механическая по определению. Прецеденты:
Этап 4 (`CrossMarketArbStrategy.ts`'s `STUB_PAIR`, но это сама стратегия — см. ниже почему
это НЕ нарушает правило), Этап 6 (11 `.publish()`→`.publishOrThrow()` сайтов в
`apps/bot/main.ts`/`apps/bot/src/bot/*.ts`), Этап 7 (`buildRiskParams()` ×2 дубликата),
Этап 8 (`buildMarketData.ts`).

`apps/bot/strategies/*`, напротив, каждый файл содержит РЕАЛЬНУЮ бизнес-логику стратегии
(собственное состояние, собственные вычисления над данными) — её нельзя механически
подогнать под новый тип без прочтения и понимания каждого файла отдельно. Ни один этап
этой миграции (1-9) не редактировал эту директорию напрямую; каждый раз, когда реальный
потребитель обнаруживался именно там (Этап 5: `IDecisionJournal`; Этап 8:
`CryptoSignalResult`/`CryptoSignalContext`; Этап 9: `IStrategy.id`/`eventStartMs`/
`CryptoSignalResult` повторно), решение — отложить до Этапа 10, вне зависимости от того,
1 это файл или 20.

**Исключение, подтверждающее правило:** `CrossMarketArbStrategy.ts` (Этап 4) технически
лежит в `apps/bot/strategies/`, но правка там касалась только литералов типа
(`STUB_PAIR.easy/hard.endEpochMs: 0` → `Timestamp.of(...)`) — не бизнес-логики файла. Это
не противоречие: правило разделяет не "какой файл трогаем", а "трогаем тип литерала
(механически) или реальное вычисление/state (нет)".

**Общий принцип для будущих этапов:** при оценке правки в `apps/bot`, спросить не "это
apps/bot?", а "это уже собранный граф зависимостей (composition root) или файл с
собственной бизнес-логикой (strategies/*)?" — первое инлайнится сейчас, второе — Этап 10,
единообразно.

### 12. Валидация на мосту между типизированным и сырым (replay/event-sourcing) мирами

**Решение:** Когда типизированный (branded ID / VO) периметр должен получать значения из
сущности, которая намеренно осталась примитивной (потому что она — event-replay/journal/
persistence формат, вне мандата миграции типов), валидация происходит РОВНО в файле, чьё
архитектурное назначение — быть мостом между этими двумя мирами. Не распространять
типизацию внутрь примитивной сущности (переоткрывать её контракт вне мандата) и не
пропускать сырое значение непроверенным через границу (оставлять её небезопасной) — третий
путь: явная валидация (`asX(...)`, Result/undefined-based) в точке пересечения.

**Обоснование:** Найдено при подключении `StrategyId` в Этапе 10b. `StrategyScheduler.
onOrderChanged(strategyId: StrategyId, ...)` получает значения из `Order`/`OrderEvent`
(`@polymarket/order`) — сущности, чей собственный докблок называет `strategyId` частью
explicit event-replay формата (`Order.fromEvents()` "воспроизводит историю без валидации").
`order`/`position` — пакеты, для которых вся эта миграция ограничена TSDoc-backfill'ом
(Этап 3), контракт `Order.strategyId: string` переоткрывать не входит в мандат ни одного
этапа. Но и `OrderEventBridge.ts` (мост между `Order`/`OrderEvent`-событиями EventBus и
`StrategyScheduler`) — не должен был бы просто прокидывать `string` дальше без проверки,
раз typed-периметр за ним ожидает `StrategyId`. Решение: оба read-сайта `OrderEventBridge.ts`
(`ORDER_REJECTED`-handler, `_notifyScheduler()`) валидируют через `asStrategyId(...)`, с
graceful skip на невалид/`undefined` — тем же способом, что уже существовавшая до этого
проверка `typeof event.strategyId === 'string' && length > 0`, просто выраженная через сам
VO-валидатор, а не ad hoc.

**Как применять:** Это не разовое решение для `StrategyId`/`OrderEventBridge` — обобщённый
принцип для ЛЮБОЙ будущей ситуации того же вида (типизированный периметр X должен принять
значение от нетипизированного периметра Y, где Y — DTO/replay/persistence-формат вне
мандата). Искать файл, чьё НАЗНАЧЕНИЕ — быть мостом (обычно уже существует, названо
`*Bridge`/`*Adapter`/`*Mapper`) и класть валидацию именно туда — не в типизированный
периметр (который тогда принимал бы неполные проверки на веру) и не в сырой периметр
(переоткрытие вне мандата).

### 13. Персистентный/routing-key паттерн не означает «всё остаётся raw»

**Решение:** На персистентной/журнальной записи с несколькими строковыми полями решение
"остаться raw" принимается ПОЛЕ ЗА ПОЛЕМ, не на весь тип разом. Идентификаторы —
брендируются (безопасно и обычно бесплатно: пишущая сторона почти всегда уже держит
branded-значение, `String(...)`-обёртка просто снимается). Raw остаются только: (а) точные
decimal-величины (сериализация без потери точности — строка, не `Decimal`/VO) и (б) поля с
подтверждённо неоднородной семантикой (routing key, несущий на практике разные типы
сущностей в зависимости от call site — брендирование как один конкретный тип было бы не
"механической недоделкой", а типовой ошибкой).

**Обоснование:** Найдено при повторном разборе `IOrderSubmissionRepository`'s
`OrderSubmissionRecord` (Этап 5) и `IDecisionJournal`'s record-типов (Этап 10c) в одной
сессии. Предыдущее прочтение `OrderSubmissionRecord` ошибочно обобщило её паттерн до
"persisted DTO ⇒ все поля остаются raw" — реальное правило оказалось: `clientOrderId`/
`venueOrderId`/`accountId`/`instrumentId` УЖЕ брендированы на этой же записи, raw остаются
только `orderPrice`/`requestedSize`/`effectiveSize` (decimal-строки, случай (а) выше) и
`strategyId?: string` (случай, предшествующий появлению реального `StrategyId`-потребителя,
не архитектурное решение). Применение этого исправленного правила к `IDecisionJournal` в
Этапе 10c дало: `strategyId`/`orderId` — брендируются на всех 5 record-типах, где
встречаются (случай "просто забыли", не "нельзя") — но `marketId` на `DecisionEntry`/
`OrderEntry`/`FillEntry`/`SignalEntry`/`CancelEntry` остаётся `string` НЕ по инерции
персистентного-DTO-паттерна, а по случаю (б): `DecisionJournalRecorder._appendRecord()`'s
собственный fallback через `_instrumentIndex` доказывает, что на ~30 из 44 реальных сайтов
конструирования это поле физически несёт `InstrumentId`-строку, а не `MarketId` — брендировать
его как `MarketId` было бы типовой ошибкой, обнаруживаемой только чтением реального
рантайм-потока данных, не структуры типа.

**Как применять:** При встрече персистентной/журнальной записи с "давно решённым" статусом
"остаётся raw, это DTO" — перепроверять поле за полем, а не доверять прежнему обобщению.
Для каждого string-поля спросить: (1) это идентификатор с существующим branded-типом и
пишущая сторона уже держит branded-значение? → брендировать. (2) это decimal-величина,
которой важна точная сериализация? → оставить строкой (не `Decimal`/VO). (3) есть
свидетельство (fallback-логика, комментарии, реальный grep по сайтам конструирования), что
поле физически несёт РАЗНЫЕ типы сущностей в зависимости от вызывающего кода? → оставить
`string`, задокументировать находку явно в TSDoc поля (не оставлять неявным).
